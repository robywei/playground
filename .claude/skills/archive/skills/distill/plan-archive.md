# 封存實作 plan 與分析文件

> 📎 [`archive:distill`](SKILL.md) 的參考檔。由 repo-template 管理，**不要直接改這裡**。

`docs/<日期>-*-plan.md` 這類實作 plan，**執行完就是歷史**，留在原處會讓下一個 agent 把它讀成現役依據。

實測：三份已完成的 plan 合計五千多行、**兩百多個 `- [ ]`**，其中兩份檔首自己寫著「已完成／已歸檔」，卻仍在服務目錄下、
checkbox 一個都沒打勾。**這比沒有文件更糟**：`- [ ] 部署 CronJob` 會被讀成待辦 —— 當初正確、現在誤導，而且沒有任何機制會發現。

## 先分清兩種 checkbox —— 錯了會把正確的東西改壞

| 性質 | 長相 | 完成後該怎樣 |
| --- | --- | --- |
| **一次性的計畫項目** | plan 裡的執行步驟（`- [ ] 建 ConfigMap`） | 打勾，或連整份 plan 一起封存 |
| **可重複的檢核清單** | 標題是「驗證清單」/「安全檢查清單」，內文寫「依序驗證」 | **永遠空著才是正確狀態** —— 不要「修成打勾」 |

看標題與前一句就能分辨。實測曾把兩份 README 的檢核清單誤判成「誤用 checkbox 當項目符號」而列進待修清單。

## 封存步驟

1. **先驗證它真的完成了，不要只信檔首的狀態標記** —— 查 plan 描述的產物存不存在（該有的模組、設定是不是新架構）。
   沒有狀態標記的那份就是靠這步才確認完成
2. `git mv` 到 `docs/history/`（保留原檔名，它已含日期）
3. **檔首加封存說明**：標明已封存、不是現役設定、**`- [ ]` 不代表完成狀態**、以及封存時的實測驗證依據
4. 🔴 **修相對路徑** —— 移動後層數全變了。若 lint 對 `docs/history/` 豁免連結檢查，**斷鏈不會被閘門抓到**，
   要自己驗一次（指令見下方）
5. 更新原本指向它的檔案，**顯示文字也要一起改**
6. ⚠️ 檔首說明若緊接原檔的 blockquote，中間要用空的 `>` 續接（MD028）
7. 🔴 **檢查 plan 裡有沒有「給 agent 的執行指示」，並在封存說明裡指名否決它** ——
   plan 模板常在檔首放一句「REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` … to implement this plan
   task-by-task」。那句話**封存之後仍然有效力**：下一個讀到它的 agent 會照著跑一輪已經做完的實作，
   而檔首只寫「本檔是歷史」擋不住它（指示比敘述具體）。實測四份裡有三份帶這句，前三份封存時都漏了。
   → `grep -n 'REQUIRED SUB-SKILL\|For agentic workers' <檔>` 掃一次再寫封存說明

## 起點是 `temp/`（gitignore）時，前提會變

| 步驟 | 服務目錄的檔案 | `temp/` 的檔案 |
| --- | --- | --- |
| 搬移 | `git mv` | **`git mv` 會失敗**（檔案不在 index）→ 用 `mv` 再 `git add` |
| 相對路徑 | 層數變了、要全改 | `temp/docs/` 與 `docs/history/` 同深度時，既有 `../../` 不受影響 |
| 閘門 | 本來就過過 | **從未受檢** —— lint 以 `git ls-files` 列舉，掃不到 `temp/` |

🔴 **最後一列最容易漏**：一份沒過過 markdownlint / 連結檢查的檔案一旦 `git add`，就換成 pre-push 擋你，
而錯誤訊息指向那份文件本身、不會說「因為這檔剛進 git」。**進 git 前先單獨跑一次 markdownlint 與連結驗證。**

⚠️ 「層數變了」只是斷鏈的**其中一種**成因。層數不變時仍要驗 —— 第二種成因是**目標檔在這段期間被刪掉了**。
死連結指向已刪除的檔案時，**改成純文字並就地說明它為什麼不在了**，不要只把連結拿掉 ——
那會讓讀者以為那個檔從來不存在。

## 逐條驗相對連結

在封存後的目錄下跑（⚠️ 用 `while` 而不是 `for`：`for x in $(...)` 會把含空白的路徑切碎）：

```bash
grep -oE '\]\((\.\./|\./)[^)#]*\)' <檔> | sed 's/^](//;s/)$//' | sort -u \
  | while IFS= read -r l; do [ -e "$l" ] || printf '❌ %s\n' "$l"; done
```

## 被否決的方案寫在現役檔，不是封存文件

下一個人問「那用 X 方案呢」時打開的是現役的 `README.md`，不是 `docs/history/` 下兩千行的分析；
封存文件只留一行指標指回現役檔那張表（怎麼寫見 [`writing.md`](writing.md)「否決一個方案時」）。

# 沉澱知識的寫法

> 📎 [`archive:distill`](SKILL.md) 的參考檔。由 repo-template 管理，**不要直接改這裡**。

## 寫護欄時寫「效果」，不要寫「手法」

實例：同一輪對話裡先寫下護欄「**別為了清狀態去故意讓告警再 fire 一次**」，幾分鐘後**用另一種手法**
（暫時縮小查詢窗 ＋ 改高頻排程）造成了完全相同的結果 —— 多發一則真告警。

護欄寫成「不要做 X 這個動作」時，只擋得住 X。同一個壞結果換個手法就繞過去了，
而且當下不會有「我正在違反自己寫的規則」的感覺。

**判準：護欄的主詞是「不可接受的結果」，不是「被禁止的動作」。**

- ❌ 「不要故意讓告警再 fire 一次」
- ✅ 「不要用任何會產生一則真通知的手法去清狀態」

寫完一條護欄，追問一句「**有沒有別的做法會造成同一個結果、而這句話擋不住？**」有就把主詞換成結果。

## 註解 / 文件漂移時：刪掉的是「副本」，不是「知識」

發現註解與實際不符時，直覺是「乾脆別寫詳細註解」。**這個直覺會連知識一起丟掉。** 先分辨兩類：

| 類型 | 會不會漂移 | 處置 |
| --- | --- | --- |
| **副本**：把別處已是權威的東西複製一份（輸出範例、格式字串、清單） | ✅ 必然 —— 改權威時要記得同步兩處，遲早漏 | **換成指標**（「實際長什麼樣直接看 X」） |
| **知識**：為什麼這樣做、踩過什麼坑、實測數字、被否決的方案 | ❌ 幾乎不會 —— 陳述的是規範或當時的實測結果；而且**沒有第二個來源** | **保留**，刪掉等於知識消失 |

🔴 **「實測數字」有一個例外，而且是最大宗的漂移源：計數型數字。**

| | 長相 | 明天會不會變 |
| --- | --- | --- |
| **行為實測**（真知識） | 「同日兩輪峰值變異 66%」「30 天全量只有 3 筆寫入」 | ❌ 那一刻就是那樣，日期錨定它 |
| **現狀計數**（其實是副本） | 「37 筆 role」「77 支 `SKILL.md`」「合計 3600 行」 | ✅ 任何人動一次就變，而且**沒有人會回頭改文件** |

實測一次全 repo 稽核：抓到的計數型數字**六處全部過時**，最舊的錯了一個多月，lint 全綠。
同一輪在寫這條修正時又寫死了一個筆數，**當場就是錯的**。

→ **判準：這個數字有沒有一條 `wc -l` / `grep -c` / `ls | wc -l` 能當場查出來？有就寫那條指令、不寫數字。**
只有「當時量到、現在複現不了」的才是知識，而那種一定要標日期。

**問一段註解「有沒有別的地方是它的權威來源」** —— 有就寫指標，沒有就保留全文。

## 否決一個方案時，連「什麼條件成立才值得重看」一起寫

被否決的方案是**知識**，要保留。但**只保留否決理由不夠**，它會往兩個相反的方向壞掉：

| 只寫理由的後果 | 長相 |
| --- | --- |
| 條件變了，沒人知道該回頭看 | 規則靜默過期 —— 當初正確、現在誤導，且沒有任何機制會發現 |
| 條件沒變，卻有人重開一輪評估 | 花掉的是真實工時，而且**可能得出不同結論**（同一批事實、不同的取樣深度） |

🔴 **判準：否決理由裡的每個「因為 X」，X 都是會變的東西 → 把「X 變了」寫成觸發條件。** 例：

| 否決理由 | 對應的重評觸發條件 |
| --- | --- |
| 撞到上游規範的結構性限制 | 上游 issue 合併，**或**供應商提供對應的私有擴充 |
| 成本約 3 倍，且該功能官方文件零記載 | 預算不再是考量時 —— ⚠️ **先開工單問，不要自己實裝試**（那條路要付費才驗得到） |
| 元件 schema 掃不到該功能的欄位 | 該元件的 schema 出現那個欄位 |

🔑 **條件要寫成「一條指令就查得出真假」的樣子。** 「某個 KV path 是不是空的」一個指令就有答案；
寫成「等它成熟後再看」就等於沒寫 —— 沒有人知道「成熟」是什麼狀態。實測一次兌現：
當初刻意收窄一條規則並在註解寫下放寬條件，近一個月後條件成立，實查兩項後**直接放寬，沒有重新評估一輪**。
（「刻意收窄一條規則」與「否決方案」是同一個模式。）

⚠️ **落點是「現役檔」，不是評估過程的封存文件。** 封存文件只留一行指標指回現役檔那張表。

## 回答完一輪分析後：分清「讀來的」與「推來的」

同一段回答裡，**引用既有文件的事實**與**當場推導出的框架**長得一模一樣 —— 都是肯定句、都有依據。
差別只在：前者已經在 git 裡，後者只存在於這段對話，**對話一刪就沒了**。

實測：被問「這些結論都有紀錄嗎」，逐條 `grep -qF` 之後 8 條命中既有文件、**2 條是當輪才推導的** ——
而那兩條正是最影響決策的那種句子。

**判準：講完一段分析，對每個關鍵句問一次「這句 `grep` 得到嗎」**，grep 不到就是本輪新增、當輪回寫進現役檔。
驗法與會讓結果反向的陷阱見 [`claude-md.md`](claude-md.md)「外放前逐項驗證」，另外再加一個：
**裸 `rg` 預設跳過隱藏目錄**，對 `.claude/` 會得到假的「沒寫過」→ 用 `grep -r` 或 `rg --hidden --no-ignore`。

## 可執行的邏輯不要以「散文」沉澱 —— 那是每次照抄一次重新實作

如果那段知識本身是一段可執行的邏輯（算範圍、組指令、判斷條件），寫成文件裡的 code block
就等於**發佈一份給人照抄的規格**。每次照抄都是一次重新實作，而重新實作會出錯。

實例：一段日期範圍的計算散在「排程腳本一份 ＋ 四個 repo 的 skill 各一份散文 snippet」，
同一輪對話內就出現**三種**「看起來對、實際錯、且不報錯」的變體：

| 變體 | 症狀 |
| --- | --- |
| `date -j -f … -v+1m`（`-v` 放 operand 之後） | 輸出預設格式、月份沒加、exit 0 |
| 月份錨點接受了另一種日期格式 | 起點跳過整段，結果一筆都不生成、無錯誤訊息 |
| `${dry:+--dry-run}` 而 `dry="0"` | 永遠帶旗標、永遠不真的執行 |

**判準**：問一句「這段內容會不會被拿去執行？」

- 會 → 落成**腳本**，文件只寫「跑這支」＋為什麼。多個 repo 都要時 → **放進共用範本**（repo-template），
  不要每個 repo 各手抄一份
- 不會（判準、踩雷、為什麼、實測數字）→ 才是散文該承載的東西

## 機制變更後：反向掃描全 repo 的過時指示

改掉一個跨檔案的機制之後（例：`CHANGELOG.md` 從手寫改為生成），**散在 repo 各處的操作指示會靜默過時** ——
它們不報錯，只是讓下一個 agent 照舊規則做事。

實測：`grep -rn 'CHANGELOG' --include='*.md'` 命中 43 個檔案，逐一判讀後只有 15 個要改。
判準是問「**這句話是叫人做事，還是陳述當時發生過的事？**」

| 命中類型 | 處置 | 例子 |
| --- | --- | --- |
| **操作指示**（「更新 X」「在 X 新增條目」「格式依照 X」） | ✅ 改 | commit 流程裡的「更新 CHANGELOG.md」 |
| **歷史引用**（拿舊紀錄當證據） | 🚫 不改 | 引用歸檔紀錄佐證某次退役 |
| **同名但指別的東西** | 🚫 不改 | 上游專案的 CHANGELOG、某個 plugin 自己的 |
| **屬於別的 repo** | 🚫 不改 | 別的 repo 的 CHANGELOG 格式 |

🔴 **第三、四類最容易誤改** —— 名字一樣、上下文看起來也像。判別法：看它周圍提到的**檔案格式與觸發機制**是不是這個 repo 的。

### 第二種觸發點：資源退役清理（比機制變更更難察覺）

機制變更是「我知道我在改規則」，所以會想到去掃。**退役清理不是** —— 清理者關注的是被退役的那個東西，
不會去想「哪些規則引用了它」。於是規則靜默過期，而且**它當初是對的**。

實例：一條規則寫「A 與 B 兩個參數缺一不可，少了 B 會落到另一個 connector」。那個 connector 後來隨某個叢集退役被刪了
（那個 commit 的主題是叢集清理），規則從此過期，沒有任何理由讓人想到去改它。

**判別法：規則說「A 缺一不可，否則會落到 B」時，去查 B 現在還存不存在。**
同型句式還有「否則會被 C 覆蓋」「不然 D 會失敗」—— 句子裡的 B / C / D 都是可退役的對象。

```bash
git log --oneline -S'<退役對象>' --all | head
git log --diff-filter=D --name-status -- '<那類路徑>' | head   ## 何時被刪、隨哪個 commit
grep -rli '<退役對象>' . --exclude-dir=.git                     ## 現存引用（再逐一分類）
```

分類時沿用上表四類 —— 描述「過去曾有」的是歷史引用，不可改；真正該改的只有把它當**現行前提**的那條規則。

🔴 **改的時候寫「規則過期」，不要寫「當初寫錯」** —— 後者會讓人不敢再寫具體理由，而具體理由正是這類文件的價值。
正確的改法是保留規則、換掉它的**理由**（例：理由從「否則會落到別的 connector」改成「不依賴『預設剛好對』這個可變前提」）。

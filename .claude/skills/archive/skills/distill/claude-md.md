# 寫進哪份文件：`CLAUDE.md` 的選擇、規則的落點、root 外放

> 📎 [`archive:distill`](SKILL.md) 的參考檔。由 repo-template 管理，**不要直接改這裡**。

## 選哪一份 `CLAUDE.md`

repo 可能有多份 `CLAUDE.md`：root 一份 ＋ 若干目錄各自一份。要即時確認：
`find . -name CLAUDE.md -not -path './temp/*' -not -path '*/history/*'`。

**預設規則：有對應子目錄 `CLAUDE.md` 就寫子目錄，root 只放全 repo 通用的。** 兩條判準都要問：

| 問題 | 答「是」 | 答「否」→ 寫子目錄 |
| --- | --- | --- |
| **① 範圍**：這條知識跨多個頂層目錄嗎？ | 例：某個慣例同時管到好幾個頂層目錄 | 例：只關某一個目錄的事 |
| **② 時機**：**動手前**就必須生效嗎？ | 子目錄檔是 **lazy-load** —— 只有讀寫該目錄檔案時才載入。「該不該做、去哪做」這種**在決定動手位置之前就要知道**的內容，寫進子目錄等於沒寫 | 「已經在改這個目錄了才需要知道」的操作細節、踩雷、指令 |

②比①更常被忽略。⚠️ **反向也要避免**：能放子目錄的別塞 root —— root **每次對話都全文載入**，
塞入細節會稀釋它、推高每次對話的固定成本。

💡 **兩者都要時的正解**：**細節寫子目錄，root 只留一行指標**，不要兩邊各寫一份。

## 規則的落點：寫在「觸發它的動作」那邊，不是「它描述的對象」那邊

同樣都該寫進 skill 或 README 時，問一句：**「誰會在什麼時候需要這條規則？」**
然後落在那個人**那時會打開的檔案**，而不是這條規則講的那個東西的說明裡。

例：「新增 X 時，Y 的放行清單是必改的一步」若只寫在**出事的那個 Y 的 README**，下次在別處新增 X 的人
打開的是 X 的建置流程，讀不到它 → 原樣重演。

| 落點 | 誰會讀到 | 結果 |
| --- | --- | --- |
| ❌ **對象文件**（出事的那個網域 / 服務 / 目錄的 README） | 只有**已經在查那個對象**的人 | 下次在**別的對象**上原樣重演 |
| ✅ **流程文件**（觸發它的那個動作的 skill / README） | 每個**做這件事**的人 | 照流程走就會被提醒 |

⚠️ **不是把對象文件那份刪掉** —— 它記的是「這裡曾經發生過什麼」，是知識、沒有第二個來源。
正解是**流程文件寫規則、對象文件留案例**，兩邊互指。

🔑 **辨識句式**：規則長成「**做 A 的時候必須 B**」「**新增 X 時 Y 是必改的一步**」時，
它的家是 **A / X 的流程**，不是 B / Y 的說明，也不是某次事故的現場。
另一個「知識在 repo 裡卻沒被讀到」的成因是**長文件的關鍵規則在後段** —— 動一個領域前把該領域的流程 skill 讀完。

## root `CLAUDE.md` 撐爆上限時：外放的驗證程序

root 有行數上限（每次對話全文載入，長度＝所有對話的固定成本；常見設 ≤ 250 行，以 `wc -l CLAUDE.md` 實查）。
distill 會一直往它加指標，所以定期要反向修剪。**修剪比新增更容易出錯**，兩條判準：

🔴 **「這條規則在別處也有」不足以構成刪除理由。** 還要問：**別處那一份，是不是「動手前必然讀到」的落點？**
子目錄 `CLAUDE.md` 只有在動那個目錄時才生效、skill 只有被叫用時才載入 →
正確的修剪是「**細節外放 ＋ root 留一行指標**」，不是「別處有了就整段刪」。
（`.claude/rules/` 底下沒有 `paths:` 的規則檔每個 session 都載入，是 root 以外唯一「動手前必然讀到」的落點。）

**那「規則本身」該留多少？看它在什麼時機發揮作用：**

| 類型 | 判準 | 落點 |
| --- | --- | --- |
| **預防性** | 改變你**怎麼寫第一道指令** —— 不知道就一定會犯（例：Bash 跑的是 zsh、產線寫入停手） | ✅ 留 root（或常駐規則檔），濃縮成祈使句 |
| **診斷性** | 只在**已經出事、正在查症狀**時用得到（例：某個錯誤訊息代表什麼） | 外放 —— 那時你本來就會開檔，root 先講一遍省不到任何一次開檔 |

⚠️ 外放診斷性內容後，root 留的那行指標要**講明分工**（例：「預防性條款見下方；症狀判讀與案例只在某檔」）。
否則下一個 agent 在 root 找不到症狀字串，會誤判成「這條規則不存在」。

### 外放前逐項驗證目標檔真的有寫

不要憑「我記得那份有」。逐 keyword 確認，而不是整段掃一次：

```bash
for kw in '訊號字串' '某個旗標' '某個判準'; do
  printf '%-20s → ' "$kw"; grep -qF -e "$kw" <目標檔> && echo 有 || echo '❌ 缺'
done
```

⚠️ 會讓這步得出**反向結論**的陷阱：

- 搜尋字串以 `-` 開頭被當成選項 → 非零退出看起來像「沒有」，於是刪掉只有 root 有的內容 → 一律 `grep -e "$pattern"`
- `for x in $(...)` 把含空白的清單切碎 → 碎片命中率變高 → 一片「有」→ 用字面清單或 `while IFS= read -r`
- **拿 root 的「濃縮寫法」當搜尋字串** → 目標檔寫的是完整形式，回「缺」是**假缺漏** →
  **報缺就換更短的詞根再查一次**才下結論
- **那個對象被改名了** → 換短詞根之後要**讀命中的原文**，確認是不是同一個對象的新名字。
  判成「缺」會往目標檔補一份**用舊名寫的**說明，比原本更糟

**留下來的是「只有 root 有」的那幾條** —— 修剪完要能說出每一條為什麼非留不可。
常見可外放的：與子目錄 `CLAUDE.md` 重複的架構敘述、目標檔已有完整版的訊號字串與旗標細節、skill 已有的決策樹。
順手刪掉**數量斷言**（「六條」「53 支腳本」），內容一增減它就靜默說謊。

🔍 lint 綠燈只證明格式與連結，**證明不了內容沒掉** —— 精簡後用 `diff <(git show HEAD:CLAUDE.md) CLAUDE.md`
逐條核對每個被刪的段落「是被外放，還是真的沒了」。

### 單節佔比是最好的下刀點

先算出每節行數：

```bash
awk '/^```/{f=!f; next} f{next}
     /^#{1,3} /{if(t!=""){printf "%4d 行  %s\n", NR-s, t} t=$0; s=NR}
     END{printf "%4d 行  %s\n", NR-s+1, t}' CLAUDE.md
```

- ⚠️ **`END` 區塊不可省** —— 沒有它，最後一節**靜默不印**，而輸出看起來是完整清單
- 🔴 **第一段 `/^```/{f=!f; next} f{next}` 不可省** —— 少了它，code block 裡的 shell 註解（`# 註解`）會被當成標題，
  **憑空生出一個最大的節**，把下刀點指到錯的地方
